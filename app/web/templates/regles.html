{% endmacro %} {% call sec('s0', '0 · Séquence de clôture (6 étapes)', true) %} Ordre d'exécution, par établissement : 1. Synchronisation des clients → 2. Génération du CSV (caisse + factures, un seul fichier) → 3. Import du CSV dans Pennylane (manuel) → 4. Cadrage de l'import par Vaelan (vérification API) → 5. Attache des justificatifs (PDF factures) → 6. Lettrage. Le tableau de suivi (page d'accueil société) trace « jusqu'à quelle date » et « réalisé le… » par étape. Couleur : vert si couvert jusqu'au dernier mois TERMINÉ (fin du mois précédent), sinon orange « mois à clôturer ». {% endcall %} {% call sec('s1', '1 · Synchronisation des clients') %} Table de correspondance TopOrder ↔ Pennylane. Clé de matching = SIRET TopOrder ↔ « Identifiant client » Pennylane (champ external_reference, où l'on met le SIRET ; PAS le SIREN qui est partagé entre établissements). Cascade de statut stricte : pas de SIRET → SIRET manquant ; SIRET sans jumeau Pennylane → absent de Pennylane ; jumeau sans compte 411 → incohérent ; jumeau + 411 → ok. Une ligne du mapping introuvable dans TopOrder → absent TopOrder. Vaelan détecte ; la correction se fait dans TopOrder/Pennylane puis on resynchronise. Les identifiants assignés (asso « ASDR ») sont gérés. {% endcall %} {% call sec('s2', '2 · Génération du CSV (caisse + factures, fichier unique)') %} Un seul CSV contenant deux journaux (Pennylane les sépare par la colonne « Code journal ») : TOSLT (caisse) et TOSLF (reclassement). Le ticket est la vérité fiscale ; tout le CA va au 70101 (= le Z).
  • Tickets anonymes → 1 écriture agrégée par jour : crédit 70101/taux + TVA collectée ; débit encaissements (CB/Espèce/TR, rendu monnaie netté) ; écart de caisse résiduel.
  • Tickets facturés → 1 écriture par facture : crédit 70101/taux + TVA ; débit 411 client du brut TTC (lettrage F<n°> = la facture) ; par paiement : débit encaissement + crédit 411 (règlement, lettré). Solde 411 restant = impayé.
Format CSV validé import Pennylane : comptes par NUMÉRO, journal par CODE (TOSLT), taux en virgule (2,1%), catégorie analytique sur TOUTES les lignes (Etablissement / nom court). Libellé de pièce « SM280526 #SMT03 » (jour en tête, lot en queue). Identifiant de lot supprimable d'un bloc. Noms de fichiers préfixés AAAAMMJJ HHMM (heure Réunion). {% endcall %} {% call sec('s2b', '2b · Pré-vol & cadrage (verrou de génération)') %} Pré-vol client (souple) : la génération est refusée uniquement si une facture de la période ne se route vers aucun compte 411 ; on liste les clients à corriger.
Cadrage : on compare le CA recalculé sur les tickets à la synthèse PDF. Le CA Total (et la période) sont BLOQUANTS. Un écart par mode de paiement (ex. CB) vient des tickets facturés payés comptant que la synthèse TopOrder classe hors « caisse ». Vaelan les RÉCONCILIE : il vérifie que l'écart est entièrement couvert par les paiements de factures encaissés en caisse (bookés au crédit du 411, lettrés F<n°>). Si oui → contrôle « COUVERT » (l'écart ne vient pas de nulle part, il est traité dans le CSV). Si l'écart dépasse les paiements de factures → avertissement « non expliqué ». Tolérance ± 0,05 €. Compte rendu PDF : Synthèse | API tickets | CSV agrégé par poste + section « Réconciliation des écarts de paiement ». {% endcall %} {% call sec('s4', '4 · Cadrage de l\'import par Vaelan (vérification Pennylane)') %} Re-jouable à tout moment. Vaelan relit les écritures des deux journaux (TOSLT + TOSLF) dans Pennylane (via l'API) et compare l'Attendu (CSV générés et stockés) à Pennylane. Le compte rendu PDF détaille tous les contrôles : CA HT / TVA / CA TTC, comptes clients 411, paiements par mode, réconciliation des paiements de factures (les paiements de factures bookés au crédit du 411 — ceux qui expliquaient l'écart de mode de paiement — sont confirmés présents dans Pennylane), et le détail par compte. Détecte toute suppression / modification / ajout depuis l'import. Horodate la dernière vérification (« c'était bon à cette date »). {% endcall %} {% call sec('s2c', 'Factures (TOSLF) & règlements — dans le même CSV') %} Reclassement (journal TOSLF, par facture) : débit 70101 / crédit 7012 (B2B) ou 70102 (B2C), HT par taux (avoirs inversés) → le CA facturé sort du 70101, net nul sur le CA total, pas de double comptage.
Écriture facture (journal TOSLT) : CA 70101/TVA + débit 411 brut (la facture) + paiements comptant (encaissement + crédit 411), lettrés F<n°>. Solde 411 = impayé.
Paiements décalés : une facture peut être réglée en caisse plus tard. Deux flux par période — CA par date de ticket ; règlements par date de paiement (liaison facture↔paiement via orderPaymentId), débit encaissement / crédit 411 F<n°>, lettrés à travers les périodes. {% endcall %} {% call sec('s8', '5 · Justificatifs (PDF factures) — par Vaelan via l\'API') %} Les écritures sont créées par import CSV manuel (sans pièce jointe). À l'étape 5, Vaelan relit les écritures « facture » dans Pennylane (pièce contenant F<n°>, journaux TOSLT créance + TOSLF reclassement), télécharge le PDF officiel de chaque facture depuis TopOrder (pdf.toporder.fr/pdf?InvoiceId=…, le GUID fait jeton, sans auth) et le rattache à l'écriture existante via l'API (POST /file_attachments puis PUT /ledger_entries/{id} avec file_attachment_id). C'est idempotent : une écriture déjà pourvue d'une pièce est ignorée. L'étape finit par une vérification dans Pennylane (champ attachment par écriture) et un rapport de complétude : nombre d'écritures facture, déjà attachées, attachées ce passage, en échec (avec la raison), couvertes au final, et le détail par facture. Vert « complet » uniquement si 0 écriture facture sans PDF. {% endcall %} {% call sec('s9', '6 · Lettrage des comptes 411 — par Vaelan via l\'API') %} Étape au niveau société (les comptes clients 411 sont partagés par les 3 boulangeries), lançable à tout moment avec une date d'arrêté (« lettrer jusqu'au … »). Vaelan lit chaque compte client tous journaux confondus (filtre par ledger_account_id) — il capte donc aussi les virements du journal de banque — et ne garde que les lignes ouvertes (lettered_ledger_entry_lines.ids vide). Il regroupe par facture (réf. F<n°>) et lettre via POST /ledger_entry_lines/lettering : soldé → lettrage complet ; acompte → lettrage partiel ; virement (crédit sans réf.) rapproché seulement si certain (une seule créance ouverte du même montant) ; ambigu / impayé → laissé ouvert et listé. Idempotent : on relit tout l'ouvert à chaque passe (un virement arrivé après coup est capté à la passe suivante — aucune hypothèse sur l'absence passée). Compte rendu : factures soldées lettrées, lettrages partiels (reste dû), virements rapprochés, ambigus à traiter à la main, créances impayées avec ancienneté. {% endcall %} {% call sec('s10', '7 · Suivi des paiements (page continue)') %} Page autonome (pas une étape de clôture séquentielle) de rapprochement TopOrder ↔ Pennylane par client (clé = compte 411, company-wide). Un job de synchro calcule un instantané par client : encours facturé impayé (solde 411 ouvert côté Pennylane), en attente de facturation (commandes TopOrder différées non facturées — statuts WAITING_FOR_BILLING / PURCHASE_ORDER —, mois courant / antérieur), exposition totale (= facturé impayé + en attente, tri par défaut décroissant), et l'écart TopOrder − Pennylane. L'API TopOrder ne permettant pas de saisir les règlements reçus, le détail d'un client liste ses virements (crédits du journal de banque) à reporter manuellement dans TopOrder : une case à cocher trace qui l'a reporté et quand (clé = ligne Pennylane, idempotent). Recherche, filtres (écart / à reporter / encours), tri colonnes, pagination.
Détail client = grand-livre complet du compte 411 Pennylane : toutes les écritures (date, libellé, journal, débit, crédit, état de lettrage) avec solde courant ligne à ligne + totaux et solde final. Chaque écriture est tagable : Saisi (reportée / rapprochée dans TopOrder) ou Ignoré (non pertinente / déjà traitée), avec traçabilité qui & quand (table PaymentReport, clé = ligne Pennylane). À venir : le côté TopOrder (factures, paiements, avoirs) en regard pour rapprocher les deux comptes ligne à ligne.
Bascule Kimayo → TopOrder : avant TopOrder, la facturation passait par Kimayo. Pour chaque client, le cutover = date de sa 1re facture TopOrder (plus ancienne créance F<n°>). On ne compte que les créances et virements à partir de cette date : les créances Kimayo antérieures sont exclues, et un virement reçu avant la 1re facture TopOrder n'est jamais retenu (on ne peut pas régler une facture pas encore émise). Règle métier : après bascule, plus de Kimayo. {% endcall %} {% call sec('cfg', 'Configuration & traçabilité') %} Tous les comptes (70101/70102/7012, TVA par taux, encaissements par établissement), journaux (code + id) et catégories analytiques sont éditables (page Configuration) ; seules les valeurs modifiées sont stockées. Chaque tâche conserve : la synthèse fournie, le CSV généré, le compte rendu PDF, la version de Vaelan et l'utilisateur. Tâches relançables ; suivi réinitialisable par établissement. {% endcall %} {% call sec('roles', 'Accès par rôle & accueil société') %} En entrant dans une société, l'utilisateur voit une page d'accueil en tuiles : seules les fonctionnalités auxquelles son rôle donne accès s'affichent. Deux rôles : comptable = tout (Suivi de clôture, Tâches, Configuration, Clients, Paiements) ; gestion (la personne TopOrder) = Clients + Paiements uniquement. Le gating est appliqué côté serveur (les routes interdites renvoient 403, même par URL directe) et la nav masque « Tâches » sans accès. {% endcall %} {% call sec('ow-export', 'OWINE — commandes internationales et export (Chrono Viti)') %} Zones (pays de livraison Shopify) : France (FR, Monaco) = circuit habituel Chrono 13 ; UE = lettre de transport seule, mais accises dues dans le pays d'arrivée dès la première bouteille (aucun seuil en accises ; stock oWine en droits acquittés sous CRD → société : DAES, qui exige l'agrément d'expéditeur certifié de l'expéditeur et un destinataire certifié ; particulier : représentant fiscal et garantie dans chaque pays) et TVA (société : autoliquidation ; particulier : TVA française sous 10 000 € HT de ventes à distance UE cumulées, puis TVA du pays de destination via l'OSS) ; hors UE et DROM-COM = export : facture commerciale bilingue en 3 exemplaires dans la pochette du colis A (1/n), rien sur les autres colis, stickers multi-pièces, EORI d'oWine, incoterm DAP (droits et taxes payés par le destinataire), vente exonérée de TVA (art. 262 I CGI), justificatif d'export à archiver.
Règles par pays = fiches pays du guide export Chrono Viti 2024 (page Douane, onglet Pays) : offre autorisée (Chrono Classic route / Chrono Express avion) selon particulier ou société, délai, limites (Suisse particuliers : Classic seul, 6 bouteilles et 10 kg par envoi → un envoi et une facture par carton au-delà de 6 bouteilles ; Japon, Corée, Chine, Australie, Taïwan… : particuliers interdits ; Royaume-Uni : Express seul, accise et TVA britanniques à l'import — la règle des 135 £ ne vise pas les produits soumis à accise ; USA particuliers : avenant Chrono Viti B2C US). Destinations interdites Chrono Viti : liste dans la configuration. « n.c. » = non communiqué → confirmer avec Chronopost.
Sur la commande (carte « International ») : type de client déduit (société si société, n° TVA ou EORI), produit Chronopost par défaut = premier autorisé, contrôles automatiques (destination, coordonnées complètes : téléphone et e-mail obligatoires, pas de boîte postale, EORI/TVA pour une société, identifiant fiscal du particulier quand le pays l'exige ; données douanières des vins : couleur, millésime, degré, code SH, origine ; valeurs HT non nulles ; limite bouteilles/envoi ; étiquettes) et étapes à cocher (coordonnées confirmées, EUR.1 au-delà de 6 000 €, signature manuelle, facture Pennylane sans TVA, OSS / accises en UE, dédouané, justificatif). Les e-mails ne partent pas tant qu'un contrôle bloquant est rouge ou que la facture commerciale définitive (numéros de colis) n'est pas générée.
Facture commerciale (modèle Chronopost « Facture commerciale Viti to B ») : n° FC-OWxxxx (ou n° Pennylane saisi), date, expéditeur avec EORI et TVA, destinataire avec téléphone, e-mail, EORI/TVA (société) ou identifiant fiscal, numéros de colis et positions dans le groupage, poids brut (1,5 kg × bouteilles) et net (brut − emballage Chrono Viti), une ligne par vin (description domaine · appellation · couleur · millésime · 75 cl · degré, origine FR, code SH/NC 22042113 blanc / 22042143 rouge), prix unitaires et totaux HT en EUR (prix Shopify ÷ 1,2 tant que la boutique prélève la TVA française ; prix tels quels si aucune TVA), port et assurance à part, usage final (revente / usage personnel), exonération de TVA, déclaration d'origine sur facture (UE préférentielle) datée, localisée et signée (image de signature de la page Douane, sinon à la main). Générée et archivée en base (versionnée) ; jointe aux e-mails Alix (à imprimer ×3) et client (copie).
Formulaire public /douane/<jeton> (FR/EN selon la langue Shopify du client) : téléphone, précisions d'adresse, particulier / société, TVA, EORI, identifiant fiscal, accord DAP → complète la commande et coche « coordonnées confirmées ». Page Douane : EORI, SIRET, capital, signature, dimensions des cartons ; données douanières des vins (couleur déduite de la référence …RB/…BB, code SH proposé, degré à saisir) ; écriture dans Shopify des codes SH, de l'origine et du poids réel des sélections ; matrice pays. Synchronisation : langue du client, TVA et port prélevés, attributs de commande (n° TVA / EORI saisis au panier), société de facturation ; tâches « formalités export » et « données douanières manquantes » pour les commandes internationales à traiter ; à l'envoi : tâches « suivre le dédouanement » (J+2) et « justificatif d'exportation » (J+15).
Zones ouvertes (v0.1.196) : page Douane › Zones = périmètre de vente (par zone : particuliers / sociétés, maximum de bouteilles par commande, multiple de 6, minimum, n° de TVA requis). Décision JS du 15/09/2026 : France (Chrono 13), Suisse particuliers, 6 bouteilles = un carton de 6 par commande, Union européenne Ouest sociétés avec n° de TVA intracommunautaire vérifié sur VIES ; tout le reste fermé (« prochainement »). Contrôle bloquant « périmètre ouvert » sur chaque commande internationale ; à l'international uniquement des cartons de 6 pleins (réf. 2036, 38 × 28 × 40 cm) ; grille de port Shopify générée = coût contrat (tarif de la tranche de poids + groupage + douane zone 4 + zone 2 hors UE + dédouanement export + éco + carburant %) + Alix (préparation 0,10 €/btl, minimum 8 €, DAE 15 € pour une société UE) + marge %, un tarif par nombre de cartons de 6 avec fenêtre de poids ± 0,1 kg (panier hors règle = aucun tarif = pas de paiement), écrite dans Shopify (deliveryProfileUpdate, droit write_shipping) en remplaçant les zones UE / International ; la zone France n'est pas touchée. Coût logistique estimé et marge affichés sur chaque commande internationale.
Degrés d'alcool : pré-remplis (fiche publique du domaine, sinon estimation) avec statut « estimé » ; confirmés vin par vin (qui, quand, source, historique) sur la page Douane, ou par la réponse d'Alix (e-mail « degrés à confirmer » envoyé depuis la commande pour les seuls vins non confirmés, réponse saisie sur la commande) ; contrôle bloquant « degrés confirmés » avant la facture commerciale ; un vin confirmé n'est plus redemandé. Sociétés UE : e-mail Alix demandant le document d'accompagnement accises (DAE / e-DSA, 15 € HT) ; contrôle VIES du n° de TVA (repli manuel « TVA vérifiée » si VIES indisponible). Site : textes FR/EN (options, politique, note de paiement) générés depuis les zones ; extrait de thème « owine-international » pour le panier (pays fermé, 6 bouteilles, multiples de 6, n° de TVA VIES via /api/owine/vies, attributs de commande) ; traduction anglaise par Claude enregistrée dans Shopify (translationsRegister) et publication de la langue (droits write_translations / write_locales). Mise en place : liste d'actions JS = tâches « Export : mise en place » (clé setup:<id>), certaines fermées automatiquement (EORI, signature, SIRET/capital, degrés).
Jalons d'ouverture (v0.1.198, 15/09/2026) : la page Douane › Mise en place range les actions par jalon ; seules celles des jalons en cours sont des tâches (titres « J1.1 — … » tenus à jour à chaque synchronisation, action cochée « fait » jamais rouverte, tâche encore ouverte d'une action repoussée retirée). Jalon 2 : Suisse, particuliers, un carton de 6 (réponses Chronopost et Alix, réglages Vaelan, préparation Shopify, envoi réel de test par commande brouillon, puis ouverture de la zone).
